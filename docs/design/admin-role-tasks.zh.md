# 管理员功能 · 分工（PR 拆分）

> 2026-10-15 · 依据 [admin-role.zh.md](admin-role.zh.md)（含第 11 节复查记录）。共 6 个 PR，按编号顺序做，前一个合并后再开下一个。
> 这两份文档随 PR 1 放进仓库，以仓库里的为准。

## 总规则（每个 PR 都适用）

1. **每个 PR 单独发布到生产都必须安全。** 管理员和组织者共用 `ORGANIZERS` 开关（Ke Li 2026-10-15 决定）。生产开关关着时，群主和成员看到的行为和现在一样，只允许下表最后一栏写明的变化。每个 PR 的测试都包括「开关关闭时行为不变」。
2. **开关只管入口，不管钱往哪走**（沿用组织者规则）。开关关时管理员按普通成员处理，他的活动照常按 `payee_id` 收款。
3. **不在各处写 `role === 'organizer'`。** PR 1 之后，「除群主外能发起活动、收款的人」一律用 `isStaff` / `currentStaffSql`，「能做什么」一律用 `can(role, cap)`。
4. 流程照旧：写 → 自动审查 → 修 → 再审查直到干净 → CI 通过后合并（rebase 到 main）。合并到 main 自动部署 staging；生产发布等 Ke Li 说「发布」。
5. 改了行为就同步改需求文档和技术设计的对应段落；PR 6 只做收尾、使用说明和演练清单。
6. 迁移只有 PR 5 一个（`0028_group_audit.sql`），它会把回滚边界移到带它的那次发布。

## PR 1 · 身份和权限底层（只改 worker 和共享类型，不改页面）

- `organizers.ts`：`Role` 加 `"admin"`；能力 `system` 拆成 `owner` 和 `data`；`ROLE_CAPABILITIES` 按设计第 4 节；`memberRole` 认 `role = 'admin'`（状态正常、没删除、开关开）；新增 `isStaff(role)`、`currentStaffSql(alias)`，`currentOrganizerSql` 的调用方全部换掉。
- `access.ts`：`ADMIN_ACCESS` 里每个 `cap("system")` 按设计 3.1 / 3.2 改成 `cap("owner")` 或 `cap("data")`；新增 `memberTarget()` 规则，用在所有 `members/:id/*` 接口上（对象是群主或任何管理员时，只有群主能做，改备注名除外）；`google_admin_required` 的报错文案不再只说群主。
- `GET /sheets`：没有 `owner` 能力时不返回 `script`。
- 把只认组织者的地方改成 `isStaff`（设计 11.4 的清单）：`transferEvent` 的目标、`handBackIfRevoked`、停用/恢复/删除成员时的「先撤销」、`telegram.ts` 的 `sendToMember` 和回退原因、`health.ts` 的转发检查和每周汇总、`inbound.ts` 的 Gmail 确认码归属、`/organizer/retire` 的身份检查、`adminEvents.ts` 新建活动时的交回检查。
- `appointOrganizer` 拒绝已经是管理员的人。
- `shared/types.ts` 的 `role` 加 `"admin"`；`export.ts` 的 `ROLE_ZH` 加「管理员」。
- **测试**：权限表测试改成「每个接口 × 群主 / 管理员 / 组织者 / 成员」四种身份；`memberTarget` 对群主、别的管理员、自己、组织者、成员各一条；`GET /sheets` 对管理员不含脚本；上面每个改成 `isStaff` 的地方各至少一条管理员的用例（测试里直接在数据库写 `role = 'admin'`）；开关关时管理员 = 成员。

## PR 2 · 任命、升降、撤销管理员

- 新文件或在 `appointments.ts` 里加：`appointAdmin`（成员或组织者 → 管理员；条件同组织者：状态正常、绑定了 Google；组织者升级时活动、收款设置、Telegram 都保留）、`demoteAdmin`（→ 组织者，活动保留）、`revokeAdmin`（→ 成员，复用撤销组织者的交回逻辑）。写入都用带条件的 `UPDATE`，防并发。
- 接口：`POST /members/:id/appoint-admin`、`POST /members/:id/demote-admin`，登记为 `cap("owner")`。撤销管理员复用 `GET/POST /members/:id/revoke`（PR 1 起已能撤销管理员，`memberTarget` 让只有群主能对管理员用）；「不再当管理员」复用 `/organizer/retire`（`self`）。
- 停用一个管理员：只有群主能做（PR 1 的 `memberTarget`），先撤销再停用。
- `GET /members`：管理员和组织者放在同一个区块（`organizers.list` 每行带 `role`，页面标题变成「管理员和组织者」），每个成员加 `isAdmin`；`canManage` 仍是 `group`（管理员能管组织者），对管理员的撤销按钮只给群主。
- 成员页按钮（只有群主看到）：「设为管理员」「升为管理员」「降为组织者」「撤销管理员」；管理员徽章。
- 任命和撤销的通知邮件，文案同组织者，写明管理员能做什么、不能做什么。
- **测试**：每种升降路径；对没绑定 Google 的人任命失败；撤销时活动的交回同组织者；并发任命/撤销；管理员调这些接口 403。

## PR 3 · 管理员的管理页面

- `GET /members` 的 `viewer` 和 `/api/auth/session` 多返回 `caps`；前端 9 处按身份字符串判断的地方（`Admin.tsx`、`AdminEvents.tsx`、`GoogleAccount.tsx`、`AdminSetup.tsx`）改成按能力判断。
- 管理员看到：待审核（可操作）、成员管理、组织者区块（可任命/撤销组织者）、所有活动和按负责人筛选、所有「待确认」、全局设置、导出、表格同步状态、转发状态、转交活动。
- 管理员看不到：群主密码、管理链接、备份密钥、清空数据、群主的 Google 绑定和收款设置、表格同步的开关和脚本、付款诊断、永久删除活动、清空「已删除」收款、删除成员。群主和别的管理员那一行没有停用/链接按钮。
- 管理员自己的设置：我的收款设置、我的 Telegram、不再当管理员（复用组织者设置页）。
- 申请人看到的「等待群主审核」「已通过群主审核」改成「等待审核」「已通过审核」（含通过邮件）。
- **测试**：e2e 各一条群主、管理员、组织者登录后看到的页面；管理员通过一个申请、停用一个成员、转交一场活动。

## PR 4 · 通知

- 新成员申请：发给群主和所有连了 Telegram 的管理员（Ke Li 决定）。只要有一个人收到就算发送成功。
- 管理员发起的活动：「发起、结算完成、收齐」抄送群主（Ke Li 决定，和组织者同一套 `sendToManagerAndOwner`）。
- 抄送和收款设置变更通知里的「组织者 X」按身份写「管理员 X」。
- 转交活动：收款人变了且操作人不是原收款人时，Telegram 通知原收款人（Ke Li 决定第 3 条）。
- 管理员 Telegram 里的「管理页面」回复 `/admin/google`（同组织者）。
- **测试**：上面每种通知的收件人；管理员没连 Telegram 时的回退；开关关时不发给管理员。

## PR 5 · 群操作记录

- 迁移 `0028_group_audit.sql`（设计第 7 节）。`清空所有数据` 的表清单加上它。
- 写入：通过/拒绝申请、停用、恢复、删除成员、重新生成链接、改备注名、任命/撤销组织者和管理员、改全局设置、导出、转交活动。群主的操作也记。
- 成员页底部「群操作记录」，群主和管理员可见，分页。
- 发布说明里写明新的回滚边界。
- **测试**：每种操作写一条，内容用人名；组织者看不到；清空数据会清掉。
