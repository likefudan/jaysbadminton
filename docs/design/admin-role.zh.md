# 管理员（admin）角色设计

> 2026-10-15 · 基于 main（4c31b85，生产 v2026.10.14）的代码。按 [admin-role-tasks.zh.md](admin-role-tasks.zh.md) 分 6 个 PR 实现中。
> 来源：Ke Li 2026-10-15 的要求。第 10 节的问题 Ke Li 已于 2026-10-15 全部决定（标 ✅）；其余是按默认做法定下的。

## 1. 一句话

管理员 = 群主减去几项「群主专属」的权力。群主任命管理员之后，可以什么都不管，由管理员管理整个网站：审核成员、管理所有活动和付款、任命组织者、改全局设置、导出数据。

| 身份 | 谁任命 | 管什么 |
| --- | --- | --- |
| 群主 | （只有一个，Ke Li） | 一切，包括下面的「群主专属」 |
| 管理员（新） | 只有群主 | 除群主专属以外的所有群管理功能，所有活动、所有付款 |
| 组织者 | 群主或管理员 | 只管自己发起（或被交给他）的活动、进自己账户的钱 |
| 成员 | 审核通过 | 报名、付款、看自己的数据 |

包含关系不变：管理员也能发起活动、收款，照常报名打球。

## 2. 代码现状：已经给管理员留好了位置

组织者功能（#74–#87）设计时就为管理员留了口子，所以这次改动不大：

- `members.role` 是没有 CHECK 的文本列，现在取值 `member` / `organizer`，加一个 `admin` 不用迁移。
- `src/worker/organizers.ts` 的 `ROLE_CAPABILITIES` 按「能力」登记权限，注释里写着「将来的管理员就是多加一行」。
- `src/worker/access.ts` 的 `ADMIN_ACCESS` 表给每个管理接口登记所需能力，没登记的接口一律拒绝。
- 现有能力：`system`（数据库级和账户安全）、`group`（管理整个群，所有活动和付款）、`events.create`、`event`、`payee`、`members.read`、`self`。

管理员基本上就是「拿到 `group`、拿不到 `system`」。难点只有两个：把 `system` 拆开（导出给管理员，其余留给群主），以及防止管理员对群主和其他管理员动手。

## 3. 权限划分

### 3.1 群主专属（管理员没有）

| 功能 | 现在的接口 | 为什么只给群主 |
| --- | --- | --- |
| 任命、撤销管理员 | （新增） | Ke Li 指定 |
| 清空所有数据 | `POST /settings/reset` | Ke Li 指定 |
| 备份 TOKEN_KEY（发到群主 Telegram） | `POST /settings/backup-key` | Ke Li 指定：密钥类 |
| 群主密码、管理链接 | `POST /settings/password`、`/settings/rotate-admin` | 群主自己的登录方式 |
| 群主的 Google 绑定 | `/settings/google*` | 群主自己的账户 |
| 群主自己的收款设置 | `POST /settings/payment` | 群主自己的钱；管理员改自己的走 `/payment-profile` |
| 永久删除活动 | `POST /events/:id/delete` | 删数据，不能恢复 |
| 「已删除」收款：永久删除、清空 | `/inbound/:iid/purge`、`/inbound/trash/clear` | 删数据，不能恢复 |
| 删除成员 | `POST /members/:id/delete` | 不能恢复（释放名字和 Google 账号）。群主专属（✅ Ke Li 决定） |
| Google 表格同步：开启、关闭 | `/sheets/enable`、`/sheets/disable` | 开启会生成新的导出密钥，旧表格会断；属于「密钥类」 |
| Google 表格同步的脚本（`GET /sheets` 里的 `script`，含导出密钥） | `GET /sheets` | 拿到脚本就能随时读全站数据，属于密钥。管理员调用 `GET /sheets` 只返回状态，不返回脚本 |
| 付款记录诊断（开关、查看） | `/payment-diagnostics` | 排查工具，里面是群主收款邮件的原文 |

### 3.2 管理员有（和群主一样）

- 待审核：通过、拒绝、重发通过邮件。
- 成员：备注名、看/复制/重新生成专属链接、停用、恢复（**对象只限普通成员和组织者**，见 3.3）。
- 任命、撤销组织者；把活动转给别人（见 3.4）。
- 全局设置（带朋友上限、网站标题、配色、排行榜、提醒时间、账单提醒、每周汇总开关）、场馆列表 ✕。
- 所有活动：修改、截止、重新开放、取消、名单、到场、费用、Finalize、标记已付、退款、催款。
- 所有收款「待确认」：关联、忽略、移回、删除到「已删除」、恢复。
- 导出 CSV（`/export/:file`）、查看 Google 表格同步状态（`GET /sheets`，不含脚本，见 3.1）、查看转发状态（`/email-status`）。
- 所有活动的操作记录，和新增的「群操作记录」（第 7 节）。
- 自己的收款设置、自己的 Telegram、「不再当管理员」。

### 3.3 管理员不能对群主和其他管理员动手

`group` 能力原来只有群主有，所以接口没检查「对象是谁」。给管理员之后要加一条规则：**管理员对群主或任何管理员（包括自己）的成员记录，不能做停用、恢复、删除、查看/重新生成专属链接、撤销、任命（包括「设为组织者」，否则等于把管理员降级）。** 改备注名可以。管理员要退出用「不再当管理员」。
- 理由：拿到群主或管理员的专属链接就能以他的成员身份报名、看账单；停用一个管理员等于撤销他，而撤销管理员是群主专属。
- 做法：`access.ts` 加一个 `memberTarget()` 规则，像现在的 `rosterRow()` 一样在进入处理函数前检查。

### 3.4 管理员能动别人的钱吗

`group` 能管所有活动，包括群主的活动。其中只有一件事会改变「钱进谁的账户」：**把一场还没 Finalize 的活动转给别人**（收款人跟着变）。比如管理员把群主还没结算的活动转给自己，这场的钱就进了管理员的账户。

✅ Ke Li 决定：管理员和群主一样能转交任何活动，规则同群主；活动的原收款人会收到 Telegram 通知，操作记录里也有一条。

已 Finalize 的活动收款人锁定，转了也只换负责人，不换收款人（现有规则）。

## 4. 能力表怎么改

```ts
export type Role = "owner" | "admin" | "organizer" | "member";
// system 拆成两个：
//   owner — 群主专属（3.1 的全部）
//   data  — 导出、表格同步状态、转发状态（只读，不改不删）
export type Capability = "owner" | "data" | "group" | "events.create" | "event" | "payee" | "members.read" | "self";

export const ROLE_CAPABILITIES = {
  owner:     ["owner", "data", "group", "events.create", "event", "payee", "members.read", "self"],
  admin:     [         "data", "group", "events.create", "event", "payee", "members.read", "self"],
  organizer: [                          "events.create", "event", "payee", "members.read", "self"],
  member:    [],
};
```

- `memberRole()`：`role = 'admin'`、状态正常、没删除、功能开关打开 → `"admin"`。
- 代码里有 32 处直接写 `'organizer'`（Telegram 发给谁、`currentOrganizerSql`、收款人资料、撤销时交回活动、Gmail 确认邮件归属等）。它们的真实含义是「除群主外、能发起活动和收款的人」，统一改成 `isStaff(role)` / `currentStaffSql`（`role IN ('organizer','admin')`），管理员就自动有了组织者的全部收款和通知能力。
- `ADMIN_ACCESS` 里 `cap("system")` 按 3.1 / 3.2 分成 `cap("owner")` 和 `cap("data")`；`members/:id/*` 改用 `memberTarget()`；新增管理员任命接口登记为 `cap("owner")`。

## 5. 登录

和组织者一样：**管理功能只在 Google 登录时可用**（`/admin/google`），不发管理链接、不设密码。
- 任命条件：已绑定 Google、状态正常。
- 别人拿到管理员的专属链接也冒充不了他：专属链接只能给还没绑定 Google 的成员关联 Google（组织者功能定下的现有规则）。
- 身份每次请求都从数据库读，撤销立即生效。
- 管理员和组织者打开的是同一个管理页面，按能力显示功能：管理员看到的和群主几乎一样，只是没有「群主专属」那一块（密码、管理链接、备份密钥、清空数据、Google 表格、诊断、永久删除按钮）。

## 6. 钱和通知

### 6.1 管理员发起的活动

和组织者一样（沿用 2026-10-04 的决定）：**钱进发起人自己的账户**，管理员要先填自己的 Venmo（和通知邮箱）、设 Gmail 转发，才能 Finalize。负责人和收款人都是他自己。管理员管理群主或别人的活动时，钱照旧进那场的收款人账户。

### 6.2 通知

| 通知 | 现在 | 有管理员之后（默认） |
| --- | --- | --- |
| 管理员自己活动的通知（截止、结算、付款、收齐等） | — | 发给管理员本人（同组织者） |
| 管理员活动抄送群主（发起、结算完成、收齐） | — | **抄送**，和组织者一样（✅ Ke Li 决定） |
| 组织者活动的抄送 | 群主 | 不变 |
| 新成员申请待审核 | 群主 | 群主 + 所有连了 Telegram 的管理员（✅ Ke Li 决定） |
| 进群主账户的「待确认」 | 群主 | 不变（按收款人发） |
| 组织者没连 Telegram 时的转发 | 群主 | 不变 |
| 系统提醒（邮件失败、转发中断、每周汇总、Gmail 确认码） | 群主 | 不变；管理员自己账户的转发和确认码发给他自己（同组织者） |
| 管理员改了自己的收款设置 | — | 发给他本人和群主（同组织者） |

### 6.3 文案

- 按「称呼人名，不称呼头衔」的规则，涉及具体某人时写名字：「付给 Amy」「由 Amy 审核通过」。
- 现在面向申请人的「等待群主审核」「已通过群主审核」改成「等待审核」「已通过审核」，因为审核的人可能是管理员。
- 徽章和权限说明里用头衔：群主、管理员、组织者。「管理员」这个词 2026-10-04 起就空出来了，现在网站上没有别的用法。

## 7. 群操作记录（新增）

现在的「操作记录」只记活动里的操作（`event_audit`）。群主放手给管理员后，需要知道谁做了群级别的事。新增迁移 `0028_group_audit.sql`：

```sql
CREATE TABLE group_audit (
  id        INTEGER PRIMARY KEY AUTOINCREMENT,
  actor_id  TEXT NOT NULL,      -- 谁做的
  target_id TEXT,               -- 对哪个成员（可空，比如改全局设置）
  action    TEXT NOT NULL,      -- approve / reject / deactivate / reactivate / delete / link_regen / note / appoint / revoke / transfer / settings / export ...
  detail    TEXT,
  at        TEXT NOT NULL
);
CREATE INDEX group_audit_at ON group_audit (at);
```

群主和管理员都能看（成员页底部「群操作记录」）。群主自己的操作也记。只加表，不影响回滚。

## 8. 任命和撤销

- **任命**（群主）：成员页对已绑定 Google 的正常成员显示「任命为管理员」；对组织者显示「升为管理员」（活动、收款设置、Telegram 都保留）。发一封通知邮件，同组织者。
- **降为组织者**（群主）：保留他的活动和收款设置，只是少了群管理权限。
- **撤销**（群主）：变回成员，和撤销组织者完全一样处理他的活动（没 Finalize 的交回群主、负责人和收款人都换；已 Finalize 的只换负责人）。
- **不再当管理员**（管理员自己）：同撤销。
- **停用**一个管理员只能由群主做，会同时撤销（同组织者现有规则）。
- 管理员人数不设上限。
- 群主可以任命、撤销组织者，管理员也可以；管理员不能任命或撤销管理员。

## 9. 和功能开关 `ORGANIZERS` 的关系

默认：**管理员和组织者共用 `ORGANIZERS` 这个开关**，不另设开关。
- 管理员依赖的东西（Google 登录进管理页、个人收款设置、多账户自动对账、个人 Telegram、任命组织者）全部是组织者功能做的，开关关着时这些入口都关着。分成两个开关会多出「管理员开、组织者关」这种半残的组合（管理员能任命组织者，但组织者用不了）。
- 开关只控制入口，不控制钱往哪走（现有原则）；开关关掉时管理员按普通成员处理，他的活动照常按 `payee_id` 收款。
- 打开开关本身不会产生任何组织者或管理员：要群主任命了才有。所以生产打开开关后，Ke Li 可以只任命管理员、不任命组织者。
- 生产开关现在是 `0`，卡 11 的 staging 演练还没做。管理员做完后，演练清单加上管理员的部分，一起演练，然后等 Ke Li 说再打开生产开关（✅ Ke Li 决定共用开关）。

## 11. 复查记录（2026-10-15，对照 main 4c31b85）

复查发现 6 处设计要补，已改进上文或在这里写明做法：

1. **`GET /sheets` 会返回导出脚本，里面有导出密钥。** 原设计把它整个给了管理员，等于把密钥给了管理员。已改：管理员只拿状态，脚本仍只给群主（3.1）。
2. **前端按身份字符串判断，有 9 处**（`Admin.tsx`、`AdminEvents.tsx`、`GoogleAccount.tsx`、`AdminSetup.tsx`）。直接加 `admin` 会让管理员看到组织者的只读页面。做法：`GET /members` 的 `viewer` 和 `/api/auth/session` 多返回一个 `caps`（能力列表），前端按能力显示，不再比较身份；`shared/types.ts` 的 `role` 加 `"admin"`。
3. **「设为组织者」会把管理员降级。** `appointOrganizer` 只拒绝已经是组织者的人，对管理员会把 `role` 改成 `organizer`。已改：3.3 的保护包括任命；`appointOrganizer` 本身也拒绝管理员，降级只能由群主用「降为组织者」。
4. **只认组织者的地方不止权限检查**：转交的目标（`transferEvent` 只接受群主或组织者）、新建活动时的交回检查（`handBackIfRevoked`）、停用/恢复/删除成员时的「先撤销」、Telegram 发给个人（`sendToMember`）、转发中断和每周汇总（`health.ts`）、Gmail 确认码归属（`inbound.ts`）、「不再当组织者」接口、Telegram 绑定（`currentOrganizerSql`）。全部改用 `isStaff` / `currentStaffSql`，按 PR 1 的清单逐个改，测试覆盖每一处。
5. **抄送和通知里写死了「组织者 X」**（`sendToPayeeAndOwner`、`sendToManagerAndOwner`、收款设置修改通知）。管理员的要写「管理员 X」。导出里的「身份」列（`export.ts` 的 `ROLE_ZH`）加「管理员」。
6. **转交活动通知原收款人**（Ke Li 决定的第 3 条）现在没有这个通知，要新写：转交改变了收款人，且操作人不是原收款人时，发 Telegram 给原收款人（群主走群主的 Telegram）。

默认不改的：
- 导出和 Google 表格里的「群主备注」「群主添加」列名不改。管理员也能写备注、代为添加，但改列名会让已经接好的 Google 表格对不上列。网站页面上的徽章已经是「代为添加」。
- 回滚：`role = 'admin'` 在旧代码里被当成普通成员（旧代码只认 `organizer`），回滚后管理员只是失去管理权限，钱的流向不受影响（按 `payee_id`）。只有 PR 5 的迁移 0028 会移动回滚边界。

没有发现需要 Ke Li 重新决定的问题。
