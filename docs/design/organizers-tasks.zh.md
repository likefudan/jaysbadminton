## 总规则（每张卡都适用）

1. **每张卡单独发布到生产都必须安全。** 生产的功能开关 `ORGANIZERS` 一直关着，直到最后一张卡。开关关着时，网站对群主和成员的行为必须和现在一样，只允许下表「开关关时生产可见的变化」一栏写明的变化（卡 1 的文案、卡 9 的操作记录、卡 10 的导出列）。每张卡的测试都要包含「开关关闭时行为不变」。
2. **开关只管「谁能进管理功能」，不管钱往哪走。** 开关只挡住任命、组织者登录管理页、给组织者发通知这些入口；账单显示谁的 Venmo、自动对账认哪个账户、谁自动算已付，永远按数据库里的收款人走，不看开关。这样万一功能上线后要紧急把开关关掉，组织者活动的钱照样能对上账，不会突然显示群主的 Venmo。
3. **数据库里 `manager_id`/`payee_id`（以及 `inbound_payments.payee_id`）为空一律当作群主。** 任何读这两列的地方都走同一个函数（例如 `eventManager(e)`、`eventPayee(e)`），不在各处自己写 `?? owner`。
4. 流程照旧：写 → 自动审查 → 修 → 再审查直到干净 → CI 通过后合并（rebase 到 main，不 merge）。合并到 main 自动部署 staging；生产发布等 Ke Li 说「发布」。
5. 每张卡改了行为就同步改需求文档和技术设计文档的对应段落（卡 11 只做收尾和通读）。
6. 迁移只有卡 2 一个（`0023`）。后面的卡如果发现还要改表，加新迁移，并在卡里写明回滚边界的变化。

## 卡 1 · 全站「管理员」改称「群主」

**为什么做：** Owner 正式叫「群主」，拥有最高权限。「管理员」这个名称留给将来可能增加的、有群管理权限的身份（Ke Li 2026-10-04），所以现在网站上指 Owner 的「管理员」要全部改成「群主」，把这个词空出来。这次新增的身份叫「组织者」。放在最前面，后面每张卡的新文案直接用新叫法。

**改动**
- 网页所有文案：管理页标题、按钮、提示、错误信息（例如「请用管理员绑定的 Google 账号登录」「联系管理员」「管理密码」→「群主密码」等）。
- Telegram 消息、发给成员的邮件（审核通过、找回链接）。
- `AdminGuide`（原「管理员指南」，改名「使用指南」，后面卡 11 要给组织者加一节）、法律页里提到「管理员」的地方。
- 导出和 Google 表格的列名：「管理员备注」→「群主备注」、「管理员添加」→「群主添加」，顺带把「Owner」列改成「群主」。
- 需求文档、技术设计文档、README 里指 Owner 的「管理员」。
- 代码里的变量名、接口路径不改（`/admin`、`is_owner` 保持），只改给人看的字。

**验收**
- `grep` 网页、worker、邮件模板里的「管理员」，结果应该为零（这个词留给将来的新身份）。
- 单元测试、e2e 里断言旧文案的地方一起改。

需求文档第 12 节「未来扩展」里的「多个管理员」两条说的是将来的身份，不改（卡 11 改写）。已执行的迁移文件里的注释不改。

**发布影响：** 只有文案，可以单独发布。

## 卡 3 · 身份解析和接口权限表

**改动**
- `admin.ts` 的中间件（现在 `/:token/*` 那段）改为解析出 `actor = { memberId, role: 'owner' | 'organizer' }`：
  - 管理链接 + 密码会话 → 群主。
  - `/google` 路径 + Google 会话 → 群主；或者 `memberRole` 为 `organizer` 的组织者（只在开关打开时）。
  - 其他一律 401。
- 每个管理接口在一张表里登记它需要的**能力**（设计第 10.1 节：`system`、`group`、`events.create`、`event`、`payee`、`members.read`、`self`），再按「身份 → 能力」对照表判断。群主拥有全部能力；不写死「只有群主」，将来加「管理员」只改对照表。几个需要说明的：
  - `event`：有 `group` 能力的人对所有活动都算，其他人只对自己负责的活动。接口参数里有账单（`/payments/:pid`）、付款记录（`/receipts/:rid`）的，先反查到活动。路径里同时有活动和子对象的（例如 `/events/:id/roster/:rid`），必须同时检查子对象属于这场活动，否则组织者可以拿自己活动的 `:id` 配别人活动的名单行来改。
  - `payee`：有 `group` 能力的人对所有收款都算，其他人只对进了自己账户的收款（`:iid`）。
  - `self`：只动自己的数据（收款设置、Telegram）。
- 中间件按表统一检查，处理函数里不再自己判断身份。
- 新建活动时负责人、收款人写成当前操作的人（群主建的仍是群主），把卡 2 里写死的「群主」换掉。
- Google 会话接口 `/api/auth/session` 返回 `role: 'owner' | 'organizer' | 'member'`，`isAdmin` 保留一段时间兼容前端，等卡 6 删掉。

**登记表（初稿，写代码时以实际路由为准）**

| 权限 | 接口 |
| --- | --- |
| system | 群主密码、管理链接、群主 Google 绑定、清空数据、导出、Google 表格、永久删除活动、已删除收款的永久删除和清空 |
| group | 成员审核 / 拒绝 / 停用 / 恢复 / 删除、查看和重新生成专属链接、重发审核邮件、填写备注名、全局设置 `/settings`、`/locations/remove`、任命 / 撤销组织者（卡 5）、活动转交（卡 5） |
| event | 活动详情、修改、立即截止、重新开放、取消、名单增改删、到场、结算预览、Finalize、标记已付、撤销付款、已退款、停止账单提醒、我的报名（self-signup / self-cancel） |
| payee | 待确认收款的忽略、移回、删除、恢复 |
| payee + event | 把待确认收款关联到账单（收款进的是自己的账户，且目标账单在自己负责的活动里；群主不受限） |
| self | 收款设置（卡 4）、Telegram（卡 7） |
| events.create | 新建活动、新建活动的默认值、场馆列表、地址联想 |
| 登录即可、按能力过滤结果 | 活动列表（没有 `group` 能力只返回自己负责的）、待确认收款列表（没有 `group` 能力只返回进了自己账户的） |
| members.read | 成员列表（含待审核、停用、已删除、组织者区块）、成员个人信息页；没有 `group` 能力时返回里去掉专属链接 |

实际登记在 `src/worker/access.ts` 的 `ADMIN_ACCESS`（卡 3 已实现）。和初稿的差别：收款设置 `/settings/payment`、Telegram、转发状态 `/email-status` 现在改的、看的都是群主自己的，卡 4、卡 7 改成每人一份之前先登记为 `system`；退出登录是「登录即可」；成员列表和个人信息页本来就不含专属链接（链接只能从 `group` 的 `/members/:id/link` 取）。

**验收**
- 一个测试遍历所有管理接口：没在表里登记的直接失败。
- 每个 `event`/`payee` 接口都用「别人的活动 / 别人的收款」打一遍，必须 403；用自己的必须成功。
- 「自己活动的 `:id` + 别人活动的名单行 `:rid`」必须 403。
- 开关关着时，`role = 'organizer'` 的成员访问 `/api/admin/google/*` 得到 401。
- 对照表测试：群主拥有全部能力；组织者恰好拥有设计里列的五项。
- 群主两种登录方式所有现有测试照常通过。

**发布影响：** 没有组织者，群主看到的完全不变。

## 卡 4 · 收款人逻辑和组织者收款设置

**改动**
- `billing.ts`：「群主自动已付」改为「本场收款人自动已付」（`ownerIds` 改成 `{ eventPayee(e) }`），包括 Finalize 后改费用时重算、被移出名单时的处理。
- `adminEvents.ts` 撤销付款时「群主的手动收款不能撤销」改为收款人的。
- 「可关联账单」里「组织者本人的不列」改为「这场收款人本人的不列」。
- 成员页（`member.ts`）的 Venmo 按钮、Venmo 用户名、Zelle 改为读 `payeeProfile(eventPayee(e))`；账单上写「付给 某某」（收款人是群主时写「付给群主」）。
- 「群主的报名特权」（不受带朋友上限、截止后到结算前仍可改，`member.ts` 的 `ownerRules`）改为「本场负责人」。
- 加名单时「临时来的人挂在谁名下」的提示改为「本场收款人或某个成员」。
- Finalize 前检查：收款人的 Venmo 用户名和通知邮箱都填了，否则拒绝并提示「请先在收款设置里填好 Venmo 和通知邮箱」（群主现在没填也能 Finalize，这条只对组织者生效，群主行为不变）。
- 组织者的「我的收款设置」接口（`self`）：读写 `payment_profiles`；Venmo 用户名、通知邮箱在群主设置和所有组织者之间唯一；有未收齐账单时修改，旧值写入 `payment_aliases`（60 天）。
- 组织者收款设置修改后发 Telegram 给群主（沿用现在「收款设置已修改」的提醒）；同时发给本人要等卡 7 的多人 Telegram，在卡 7 补上。
- 群主保存自己的收款设置时也要检查唯一性（不能和任何组织者的现用或 60 天内的旧账户相同）。群主自己改 Venmo 的行为不变：不进 `payment_aliases`，和现在一样立即只认新账户。
- 收款人一旦有账单（第一次 Finalize 之后）就锁定：`payee_id` 不能再改（卡 5 的转交会用到这条检查）。

**验收**
- billing 测试：收款人是组织者时，组织者自己和挂在他名下的朋友自动已付，群主的账单是未付；Finalize 后改费用、移出名单的各种情况都按收款人算。
- 收款人是群主（或为空）时所有现有 billing 测试不变。
- 唯一性：两个人填同一个 Venmo 用户名被拒绝；和群主的相同也被拒绝。
- 改 Venmo 后旧值进了 `payment_aliases`。

**发布影响：** 开关关着时没有组织者的活动，收款人都是群主，行为不变。

## 卡 5 · 任命 / 撤销组织者

**改动**
- 群主成员列表每人加「设为组织者 / 撤销组织者」（开关关着时不显示，接口也拒绝）。任命条件：状态正常、已绑定 Google。任命后发一封邮件给对方（邮件服务没配置时只在页面提示群主自己告诉他）。
- 组织者自己在设置里可以「不再当组织者」，规则同撤销。
- 成员页（群主和组织者都能看到）：组织者名字旁边显示「组织者」标记；成员列表最上面单列一个「组织者」区块，每人一行显示：任命时间、收款设置是否填好、转发是否生效（最近一次收到他账户的 Venmo 邮件）、Telegram 是否连接、他负责的未归档活动数。历史收款人（撤销后还有收款中的活动）也列在这里，标「已撤销，还有 N 场在收款」。
- 以前当过组织者的人再次任命时，沿用他原来的 `payment_profiles` 那一行，清掉 `retired_at`。
- 撤销时（设计第 8 节表格）：
  - 未 Finalize 的活动：`manager_id`、`payee_id` 都改为群主。
  - 已 Finalize、未归档：`manager_id` 改为群主，`payee_id` 不变。
  - 不管有没有这类活动，他的 `payment_profiles` 都标 `retired_at`。
  - 撤销前弹窗列出会受影响的活动。
- 历史收款人失效：所有 `payee_id` 是他的活动都归档（或取消、删除）以后；撤销时就没有这类活动的，撤销那一刻就失效。卡 8 用到。
- 撤销后他进不了管理页，所以撤销时发一封邮件告诉他：哪几场活动的钱还会继续付到他的账户、由群主接手管理，请他收到钱后和群主核对；以及等这些活动收齐后（或现在就可以，如果没有）删掉 Venmo 邮件转发过滤器。
- 停用一个组织者时先自动撤销；删除成员时增加检查「不是任何未归档活动的收款人」。
- 群主可以把 Finalize 之前的活动转给另一个组织者或自己（负责人和收款人一起改）；Finalize 之后、归档之前只能改负责人；已归档、已取消的活动不能转。
- 安全前提：现在成员用专属链接关联 Google 时，只有 `google_sub` 为空才能关联（`googleAuth.ts` 的 `UPDATE ... AND google_sub IS NULL`），成员也不能自己解绑。所以「任命时必须已绑定 Google」保证了别人拿到组织者的专属链接也无法换绑自己的 Google 来冒充他。这两条现有规则不能改，加测试锁住：对组织者用专属链接关联另一个 Google 账号必须失败。

**验收**
- 群主和组织者在成员页都能看到组织者区块和标记，内容正确；组织者看不到「设为 / 撤销组织者」按钮，直接请求任命 / 撤销接口得到 403。
- 撤销的三种活动状态各有测试；撤销后他的 Google 会话下一次请求管理接口就是 401（和非组织者一样）。
- 停用组织者会先撤销；删除被检查挡住。
- 转交：Finalize 前收款人跟着变，Finalize 后不变。
- 开关关时按钮不出现，接口 403。

**发布影响：** 开关关着时不可见。

## 卡 6 · 组织者的管理页

**改动**
- 组织者用 Google 登录后，账号页和活动页出现「管理」入口，打开 `/admin/google`。
- `Admin.tsx` 按 `role` 显示标签页：组织者有「活动」「收款」「待审核」「成员」「设置」。「待审核」「成员」两页对组织者是只读的：内容和群主看到的一样（Ke Li 2026-10-04 决定），但没有通过 / 拒绝 / 停用 / 恢复 / 删除 / 链接 / 备注名 / 任命 / 撤销这些按钮。
- 活动标签：组织者只看到自己负责的活动；群主看到全部，每场显示负责人，可以按负责人筛选。
- 新建活动的表单对组织者可用（接口在卡 3 已经把负责人、收款人设成发起人）。
- 「记住上次的值」（时间、截止提前量、球价）按发起人分别记，存在 `settings` 的 `last_xxx:<成员编号>` 键里（不用改表）。最近场馆列表仍然大家共用。
- 名单「添加人员」和群主一样，从正常状态的成员里选。
- 设置标签：组织者只看到「我的收款设置」（含 Gmail 转发步骤、转发确认码、「转发已生效」状态，后两项卡 8 才有数据）、「我的 Telegram」（卡 7 接上）、「不再当组织者」。
- 场馆列表的 ✕ 只对群主显示。
- 成员资料里「备注名（只有群主能看到）」的提示改成「只有群主和组织者能看到」（开关关时仍显示原文）。
- 登录成员看到的活动卡片上显示「组织：某某」（公开页不显示）。
- 前端不再用 `isAdmin`，删掉卡 3 留的兼容字段。
- 检查组织者能调用的每个接口的返回内容（成员列表、个人信息、活动详情、名单、结算、收款列表）：不能含成员的专属链接。现在这些接口是按「只有群主能看」写的，可能顺带返回了链接，按身份裁掉。

**验收**
- e2e（用测试里现有的 Google 会话模拟）：群主任命一位组织者 → 组织者用 Google 登录 → 发起活动 → 成员报名 → 组织者改名单 → 填费用 → Finalize（未填收款设置时被拦）→ 成员页显示组织者的 Venmo。
- e2e：组织者能看到成员页和待审核，但没有操作按钮；看不到别人的活动；直接请求群主专用接口得到 403。
- 单元测试：以组织者身份请求上面这些接口，返回里没有专属链接。

**发布影响：** 开关关着时不可见。

## 卡 7 · 多人 Telegram 和通知分发

- `sendToOwner` 之外加 `sendToManager(event)`：发给本场负责人；负责人没连 Telegram、已经不是组织者、或者开关关着时，发给群主，消息开头注明原因（例如「组织者 某某 还没连接 Telegram」）。

  - 发给负责人：截止前提醒、报名截止、结算提醒、结算完成、每日收款汇总和催款文字、收齐、部分付款、多付。
  - 抄送群主（负责人不是群主时）：新活动发起（这是新增的消息，现在群主自己建活动不发）、结算完成、收齐。

**发布影响：** 开关关着时只有群主，消息和现在一样。

## 卡 8 · 多收款人自动对账

**改动**
- `inbound.ts`：按「Sent to」+ To 找收款人（群主 `settings` → `payment_profiles` → `payment_aliases`），找到的写进 `inbound_payments.payee_id`。
- 找到账单后比较本场收款人：不一致 → 「待确认」，原因「付到了 @xxx（某某）的账户，但这场的收款人是 某某」。
- 历史收款人（`retired_at` 有值）：
  - 还有他收款的未归档活动 → 照常对账；对不上的进「待确认」，由群主处理（他已经没有管理权限）。
  - 已经失效 → 带本群付款编号的进「待确认」（`payee_id` 是他，群主处理）；其他邮件静默丢弃，不报「收款账号不一致」。
  - 「失效」发生在撤销时（没有收款中的活动）或他收款的最后一场活动收齐归档、被取消、被永久删除的那一刻：在这四个地方检查一次，失效时发邮件提醒他删除转发过滤器（他的 Telegram 已在撤销时断开），同一人只提醒一次。卡 5 撤销时那封邮件已经说了的话，这里不重复发。
- 找不到任何收款人 → 和现在一样报「收款账号不一致」给群主（每天最多一次）。
- 收款标签：组织者只看到 `payee_id` 是自己的待确认 / 已忽略 / 最近关联；关联时可选的账单只有自己负责的活动；群主看全部，每笔显示进了谁的账户。
- 关联「钱在别人账户」的收款时，账单和收款记录上标注「钱在 某某 的账户」。这个信息从 `inbound_payments.payee_id` 推出来，不加列。
- 在账单里撤销一笔 Venmo 付款时（回到待确认）：从待确认关联来的那笔沿用原来的 `payee_id`；自动对账记上的那笔新建待确认，`payee_id` 填这场的收款人（自动对账只有收款人对得上才会直接记账）。
- Gmail 转发确认邮件：按邮件内容里的邮箱匹配组织者的 `venmo_email`，找到就存进他那行的 `gmail_confirm`（设置页显示，24 小时后清掉），他连了 Telegram 就同时发一份；找不到的发群主（和现在一样）。
- `payment_profiles.email_last_at` 每收到一封该账户的 Venmo 邮件就更新；设置页据此显示「转发已生效」。
- 「转发可能中断」按收款人检查：收款人是现任组织者 → 发给他（没连 Telegram 则发群主）并抄送群主；收款人是群主或历史收款人 → 发群主。
- 待确认的通知按同样的规则发：现任组织者账户的发给他（没连则群主），群主和历史收款人账户的发群主。

**验收**
- inbound 测试：钱进群主账户 / 组织者账户 / 旧账户（alias）/ 历史收款人（未失效、已失效）/ 陌生账户，各自结果正确。
- 付错人：群主活动的钱进了组织者账户 → 待确认，组织者看得到但不能关联，群主能关联。
- 所有现有 inbound 测试（只有群主）结果不变。
- 用一位组织者的真实转发邮件在 staging 测一次（需要 Ke Li 找一位组织者配合）。

**发布影响：** 开关关着时只有群主的账户，行为不变。
