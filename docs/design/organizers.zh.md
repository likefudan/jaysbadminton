# 组织者功能设计（原「多管理员」）

> **状态：设计中，尚未实现。** 这里描述的行为和现行的 [需求文档](../requirements.zh.md)、[技术设计](../technical-design.md) 有冲突时，以现行文档为准；任务卡 11 完成后，本设计的内容并入需求文档。

> 2026-10-04 · 只是设计，没有改代码。基于生产版本 v2026.10.03.5 的代码和 `docs/requirements.zh.md`。
> 标 ★ 的三个问题 Ke Li 已于 2026-10-04 决定（见第 12 节）：钱进活动发起人的账户；组织者只用 Google 登录；群主只收三条抄送。其余是自问自答后选的默认做法。

## 1. 三种身份

| 身份 | 是谁 | 一句话权限 |
| --- | --- | --- |
| 群主（Owner） | 现在的「管理员」，只有一个（Ke Li） | 一切权限，包括所有活动、成员审核、全局设置、数据库级操作 |
| 组织者（新增） | 群主从成员里任命，可以有多个 | 发起活动、为自己的活动收款；只能管理**自己发起（或群主交给他）的活动** |
| 成员 | 现在的普通成员 | 报名、付款、看自己的数据 |

包含关系：群主也是组织者，组织者也是成员。组织者和群主照常报名打球、出现在名单和账单上。

界面上的叫法统一改为：**群主**（原来的「管理员」字样全部改成「群主」）、**组织者**、**成员**。新身份原来叫「管理员」，Ke Li 2026-10-04 改名为「组织者」：它的权限是发起活动、收款、管理自己的活动，不管理这个群。代码里对应 `organizer`。

「管理员」这个名称留给将来：Ke Li 可能以后增加有群管理权限的管理员（介于群主和组织者之间）。这次不做，但设计要给它留位置：身份用一个可以扩展的 `role` 值（`owner` / `organizer` / `member`，将来加 `admin`），接口权限表按「能力」登记而不是写死「只有群主」，到时候给新身份分配能力就行，不用推倒重来。网站上现在指 Owner 的「管理员」全部改成「群主」，把这个词空出来（任务卡 1）。这一步本身要扫一遍所有文案、Telegram 消息和文档。

## 2. 核心问题：组织者的活动，钱进谁的账户？ ★

这是整个功能最难的地方。现在所有收款都绑在群主身上：账单上的 Venmo 按钮是群主的用户名，自动对账只接受「收款账号 = 设置里的 Venmo 用户名」并且「收件邮箱 = 设置里的 Venmo 通知邮箱」的邮件，群主本人的账单自动算已付。

**已选定：组织者自己收（方案 A）**
- 每场活动有一个**收款人**，默认是发起人。组织者发起的活动，成员的 Venmo 按钮和 Zelle 账号显示的是组织者自己的。
- 这才符合「组织者拥有收款的权利」；群主不用替别人收钱再转账，场地费是谁垫的谁收。
- 代价：自动对账要支持多个收款账户（见第 6 节），组织者要自己填 Venmo 并设 Gmail 转发过滤器；转发没设好时只能手动标记（和现在的 Zelle 一样）。

（另一个方案是钱统一进群主账户、组织者只管组织。改动小，但群主要再转钱给垫付场地费的人，组织者也没有真正的收款权，Ke Li 没有选。）

## 3. 组织者的登录方式 ★

现在：群主用「管理链接 + 密码」或绑定的 Google 账号；成员用专属链接或 Google 登录。专属链接是「可以转发、别人拿到就能冒充」的（需求文档里列为可接受的风险），这对普通成员可以接受，但对能改名单、标记付款、退款的组织者不够。

**已决定：组织者的管理功能只在 Google 登录时可用。**
- 任命条件：该成员已绑定 Google 账号，状态正常。
- 这条条件同时是安全保证：现在专属链接只能给**还没绑定** Google 的成员关联 Google，成员也不能自己解绑。所以别人拿到组织者的专属链接，也没法换成自己的 Google 来冒充他。这两条现有规则要加测试锁住。
- 组织者用专属链接打开时，仍然是普通成员页面，页面上提示「管理功能请用 Google 登录」。
- 不给组织者发管理链接、不设管理密码：少一套密码就少一套找回、锁定、泄露的流程。
- 撤销组织者后立即生效：每个请求都从数据库读身份，而不是把身份写进会话。

群主的登录方式不变（管理链接 + 密码，或 Google）。

| 取消活动（Finalize 前） | 所有活动 | 本场 | ✗ |
| **永久删除活动** | ✓ | ✗ | ✗ |

## 5. 数据模型

新增迁移 `0023_multi_admin.sql`（示意）：

```sql
-- 身份：is_owner 保留（群主只有一个）；其他人用 role，将来加「管理员」只是多一个取值
-- 不加 CHECK 约束：SQLite 改 CHECK 要重建整张表，取值由代码校验
ALTER TABLE members ADD COLUMN role TEXT NOT NULL DEFAULT 'member';   -- 'member' | 'organizer'（将来可能有 'admin'）
ALTER TABLE members ADD COLUMN role_since TEXT;

-- 每场活动的负责人和收款人（迁移时都回填为群主；下面 inbound_payments.payee_id 也一样）
ALTER TABLE events ADD COLUMN manager_id TEXT REFERENCES members (id);
ALTER TABLE events ADD COLUMN payee_id   TEXT REFERENCES members (id);
CREATE INDEX events_manager ON events (manager_id);   -- 组织者的活动列表按负责人查
CREATE INDEX events_payee ON events (payee_id);

-- 组织者的收款设置（群主的仍留在 settings 里，不搬，见下方「回滚注意」）
CREATE TABLE payment_profiles (
  member_id      TEXT NOT NULL PRIMARY KEY REFERENCES members (id),
  venmo_username TEXT COLLATE NOCASE UNIQUE CHECK (venmo_username != ''),   -- 没填时存 NULL，不存空字符串
  venmo_email    TEXT COLLATE NOCASE UNIQUE CHECK (venmo_email != ''),
  zelle_account  TEXT,
  email_last_at  TEXT,          -- 最近一次收到这个账户的 Venmo 邮件（健康检查、「转发已生效」用）
  gmail_confirm  TEXT,          -- 最近一封转发确认邮件的内容（显示在收款设置页，24 小时后清掉）
  gmail_confirm_at TEXT,
  retired_at     TEXT,          -- 撤销组织者后成为「历史收款人」的时间
  updated_at     TEXT NOT NULL
);

-- 改过的 Venmo 用户名/通知邮箱，继续认 60 天
CREATE TABLE payment_aliases (
  venmo_username TEXT COLLATE NOCASE NOT NULL,
  venmo_email    TEXT COLLATE NOCASE NOT NULL,
  member_id      TEXT NOT NULL REFERENCES members (id),
  until          TEXT NOT NULL,
  PRIMARY KEY (venmo_username, venmo_email)
);

-- 收款进了谁的账户
ALTER TABLE inbound_payments ADD COLUMN payee_id TEXT REFERENCES members (id);
UPDATE inbound_payments SET payee_id = (SELECT id FROM members WHERE is_owner = 1);
CREATE INDEX inbound_payee ON inbound_payments (payee_id, state);   -- 组织者的「待确认」列表

-- 组织者的 Telegram 接收人（群主的仍留在 settings 里）
CREATE TABLE telegram_bindings (
  member_id TEXT NOT NULL PRIMARY KEY REFERENCES members (id),
  chat_id   TEXT UNIQUE,        -- 还没连上时为空（SQLite 的 UNIQUE 允许多个空值）
  chat_name TEXT,
  bind_hash TEXT,               -- 这个人的一次性绑定码（SHA-256），点「连接 Telegram」时写入，连上后清空
  bind_expires TEXT
);

-- 操作记录
CREATE TABLE event_audit (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  event_id   INTEGER NOT NULL,
  actor_id   TEXT NOT NULL,     -- 谁做的（群主也记）；自动对账记 'system'
  action     TEXT NOT NULL,     -- roster_add / fee_edit / mark_paid / refund / reassign ...
  detail     TEXT,              -- 简短描述，例如「把 Alice 移出名单」
  at         TEXT NOT NULL
);
CREATE INDEX event_audit_event ON event_audit (event_id, at);
```

为什么分开 `manager_id`（负责人）和 `payee_id`（收款人）：
- 平时两者相同。
- 撤销组织者时，已经 Finalize 的活动要换人管理，但钱已经在往原收款人的账户里付，收款人不能跟着换（见第 8 节）。
- 收款人在**第一次 Finalize 之后锁定**，不能再改：已经发出去的账单和成员付款都指向这个账户。Finalize 之前群主把活动转给别人时，收款人跟着变。

关于「记住上次的值」：开始/结束时间、截止提前量、球的单价改为按发起人分别记（`settings` 里加 `last_xxx:M003` 这样的键），不然两个组织者会互相覆盖默认值。

**`manager_id`/`payee_id` 为空一律当作群主。** 迁移时回填为群主编号，但代码不依赖回填：旧代码（回滚时）新建的活动这两列是空的，新代码照样当成群主的活动。

回滚注意：
- 群主的收款设置（`venmo_username` 等）和 Telegram（`telegram_chat_id`）**继续存在 `settings` 里，不搬家**。新表只存组织者的数据。这样在功能还没打开之前，回滚到 0023 之前的版本也不会丢群主的设置，不需要双写。
- 迁移只加列、加表，旧代码技术上可以照常运行；但按现有规则（不回滚到缺少已执行迁移的版本），带 0023 的版本发布后，回滚边界就移到这个版本。
- 功能打开、有了组织者的活动以后，不能再回滚到不认识 `payee_id` 的版本（见第 11 节）。

## 6. 收款与自动对账（方案 A）

### 6.1 组织者的收款设置
- 组织者在「我的收款设置」里填 Venmo 用户名、Venmo 通知邮箱（Venmo 账户登记的邮箱）、Zelle（选填），和群主现在的设置页一样。
- Venmo 用户名和通知邮箱全系统唯一：两个人填同一个账户会让系统分不清钱进了谁的口袋。
- 必须填好 Venmo 用户名和 Venmo 通知邮箱，才能 **Finalize**（可以先建活动、收报名，不卡住）；Zelle 选填。设置页附上 Gmail 转发过滤器的设置步骤，收到第一封 Venmo 邮件后显示「转发已生效」。
- 有未收齐的账单时修改 Venmo 用户名或通知邮箱：允许，但弹窗提醒「已经发出的账单的付款按钮会立即换成新账户，旧账户收到的付款还会继续认」。旧的用户名和邮箱存进 `payment_aliases` 表（见第 5 节），继续接受 60 天。

### 6.2 自动对账怎么区分收款人
仍然只有一个转发地址 `venmo@jaysbadminton.llmat.dev`，每个收款人在自己的 Gmail 里设同样的过滤器转发过来。系统收到邮件后：

1. DKIM 校验不变（必须是 venmo.com 签名）。
2. 用正文里的「Sent to」（收款 Venmo 用户名）和邮件收件人（To）找**同时匹配**的收款人：依次查群主的设置（`settings`）、组织者的 `payment_profiles`（包括历史收款人）、`payment_aliases`（60 天内改过的旧账户）。找不到 → 和现在的「收款账号/收件邮箱与设置不一致」一样，按现有规则提醒群主（每天最多一次）。
3. 按备注里的付款编号找账单（现有逻辑不变）。
4. **新增一步：账单所在活动的收款人必须等于第 2 步的收款人。** 对不上（比如成员把群主活动的钱付给了组织者）→ 进「待确认」，原因写「付到了 @xxx（组织者 A）的账户，但这场的收款人是群主」。
5. 其余规则（部分付款、多付、归档后多付、去重）完全不变。

「待确认」怎么处理付错人的钱：
- **只有群主**能把它「关联到账单」（因为账单属于别人的活动，组织者没有那场的权限）。关联后照样记成已付，并在账单和操作记录上标「钱在组织者 A 的账户」，两人自己私下结算。
- 收到钱的组织者能看到这笔，可以「忽略」并把钱退给付款人，请他重新付。

### 6.3 Gmail 转发确认邮件
现在 Google 发来的「确认转发地址」邮件会转到群主的 Telegram（`inbound.ts` 的 `gmailConfirmation`）。改为：按邮件里提到的 Gmail 地址匹配组织者的 Venmo 通知邮箱，找到就把确认内容存到他的收款设置页（24 小时内显示），他连了 Telegram 的话同时发一份；找不到对应的组织者仍发群主（和现在一样）。组织者的 Venmo 账户不一定登记的是 Gmail（可能是 Outlook 等）：只要那个邮箱能设「自动转发 Venmo 邮件」就行，设置页的步骤按 Gmail 写，其他邮箱给出通用说明。

### 6.4 账单和成员页
- 成员页每张账单写明「付给 组织者 A」以及 A 的 Venmo/Zelle。同一个成员同时欠群主和组织者的钱时，按活动分开显示（现在已经是按活动分开）。
- 付款编号格式不变：`用户名-jbm20261006-m007`。活动编号本来就唯一，两个组织者同一天各发起一场会自动变成 `jbm20261006` 和 `jbm20261006b`，不需要改。
- 分摊取整多出的几分钱归收款人（现在写的是「归 Owner」）。
- 「自动算已付」从「群主本人」改为「**这场的收款人本人**」：组织者自己活动里，组织者和挂在他名下的朋友自动已付；群主去打组织者的球，要付钱给组织者，和别人一样。
- 临时来的非成员挂在谁名下，规则从「群主或某个成员」改为「本场收款人或某个成员」。
- 群主本人现有的报名特权（不受带朋友上限、截止后到结算前仍可改）改为给**本场负责人**；群主在别人的活动里需要改名单时，直接用管理页（群主对所有活动都有权限）。

### 6.5 退款
钱在谁的账户谁退。「需要退款」列表和「已退款」按钮给本场负责人（以及群主）。如果负责人和收款人不是同一个人（撤销组织者后的情况），页面提示「钱在 A 的账户，请联系 A 退款」。

## 7. 通知（Telegram）

- Telegram 机器人从「只认一个接收人」改为「每人一个」：群主和每个组织者各自在设置页「连接 Telegram」。现在的一次性绑定码只有一个（`settings` 里的 `telegram_bind_hash`），两人同时连接会互相覆盖，要改成按人存（绑定码里带上成员编号）。机器人只回应已连接的账号，其他人发消息照样忽略。「管理页面 / /admin」命令只对群主有效。
- 每场活动的通知（截止前提醒、截止、结算提醒、结算完成、每日收款汇总和催款文字、收齐、部分付款、多付）发给**本场负责人**。负责人没连 Telegram、已经不是组织者、或者功能开关关着时，退回发给群主，并在消息开头注明原因（例如「组织者 A 还没连接 Telegram」）。
- 「待确认」按收款人发：钱进了现任组织者 A 的账户就发给 A；进了群主或历史收款人的账户发群主。
- 全局的系统通知（入群申请、Venmo 邮件异常、签名失败、每周健康简报、Google 表格同步失败）只发群主。
- 「转发可能中断」改为按收款人检查：A 有账单发出 3 天以上没付清、3 天内也没收到 A 账户的任何 Venmo 邮件，就提醒 A（抄送群主）。A 已经被撤销（历史收款人）时只发群主。
- 群主抄送 ★（已决定）：负责人不是群主时，只抄送三条：「新活动发起」「Finalize 结算完成」「收齐」。其他群主随时可以在管理页看。
- 发给组织者的消息里「请打开管理页」的链接要指向组织者的入口（Google 登录后的「管理」），不能用群主的管理链接（现在 `telegram.ts` 拼的是 `/admin/<令牌>`）。
- 微信群文字里加上组织者，例如「本周活动（组织：A）报名已截止…」；负责人是群主时不加，和现在一样。

## 8. 任命和撤销组织者

### 任命
- 群主在成员列表点某人 →「设为组织者」。条件：状态正常、已绑定 Google（第 3 节）。以前当过组织者的人再次任命时，沿用他原来的收款设置，清掉「历史收款人」标记。
- 任命时可选发一封邮件告诉对方（用现有邮件服务），内容是「你已成为组织者，用 Google 登录后在『管理』里发起活动；先填收款设置」。
- 人数不设上限。
- 群主（以及只读的组织者）在成员页能一眼看到谁是组织者：名字旁边有「组织者」标记，成员列表最上面有一个「组织者」区块，列出每位组织者的任命时间、收款设置是否填好、转发是否生效、Telegram 是否连接、负责的未归档活动数，以及已撤销但还有活动在收款的人。

### 组织者自己退出
- 组织者可以在设置里点「不再当组织者」，规则和群主撤销一样。

### 撤销（群主操作，立即生效）
撤销前弹窗列出他负责的未归档活动，以及每场会怎么处理：

| 活动状态 | 负责人 | 收款人 |
| --- | --- | --- |
| 报名中 / 已截止（未 Finalize） | 转给群主 | 转给群主（成员还没看到账单，换人没有影响） |
| 已 Finalize、收款中 | 转给群主 | **不变**，仍是原组织者：钱已经在往他的账户付，自动对账继续认他的账户，直到活动收齐归档 |
| 已收齐 / 已取消 | 不变（只是历史记录） | 不变 |

- 撤销时断开他的 Telegram；之后和他有关的提醒（待确认、转发中断）都发给群主。他账户里收到的、还在收款中的活动的「待确认」由群主处理。
- 撤销后他的收款设置保留为「历史收款人」，只用于继续认那些还在收款中的活动的 Venmo 邮件；所有他收款的活动都归档后自动失效（撤销时就没有收款中的活动的，立即失效）。
- 撤销后他进不了管理页，所以撤销时发邮件告诉他：哪几场的钱还会继续付到他的账户（由群主接手管理，收到钱后和群主核对），以及什么时候可以删掉转发过滤器。
- 失效以后，他的 Gmail 可能还在把所有 Venmo 邮件转过来。这些邮件要**静默丢弃**，不能当成「收款账号不一致」天天提醒群主；系统在失效时发邮件提醒他删掉转发过滤器（他的 Telegram 撤销时已经断开）。历史收款人账户里收到的、带本群付款编号的钱仍进「待确认」（钱是群里的人付的）。
- 他已经登录的 Google 会话下一次请求就没有管理权限了（每次请求读数据库）。

### 和停用/删除成员的关系
- 停用一个组织者：先自动执行一次「撤销组织者」（上表），再按现有停用规则。
- 删除成员：现有规则已经要求「没有欠款、不在任何还没收齐的活动名单上」；再加一条「不是任何未归档活动的收款人」。

### 把活动转给别人（群主）
群主可以把一场 Finalize 之前的活动的负责人改成另一个组织者或自己，收款人一起换；Finalize 之后只能换负责人，收款人锁定。

## 9. 操作记录

多人管钱以后，「谁改的」变得重要（比如成员说「我付过了」，账单却被撤销了）。每次改名单、到场、费用、Finalize、标记付款、撤销付款、退款、转交、取消，都在 `event_audit` 记一条：谁、什么时候、做了什么。活动页底部可以展开「操作记录」。群主看全部，组织者看本场。成员看不到。

## 10. 实现要点

### 10.1 身份判断集中到一处
现在的写法是：`/api/admin/:token/*` 用管理链接 + 密码会话（或群主的 Google 会话）整体放行，后面所有处理函数默认「调用者是群主」。改成：

1. 中间件解析出 `actor = { memberId, role: 'owner' | 'organizer' }`：群主的两种登录方式照旧；组织者只认 Google 会话 + `role = 'organizer'` + 状态正常 + 功能开关打开。
2. 每个接口在路由表里登记它需要的**能力**，而不是写死「只有群主」。另有一张「身份 → 能力」对照表：群主拥有全部能力；组织者拥有 `events.create`、`event`、`payee`、`self`、`members.read`；将来的「管理员」只要在对照表里加一行。能力分为：
   - `system`：数据库级和账号安全（永久删除活动、清空数据、群主密码、管理链接、群主 Google 绑定、导出、Google 表格、永久删除收款）。
   - `group`：管理这个群（成员审核 / 停用 / 恢复 / 删除、专属链接、备注名、全局设置、场馆删除、任命 / 撤销组织者、转交活动、管理所有人的活动和收款）。
   - `events.create`：发起活动。
   - `event`：管理这场活动（有 `group` 能力的人对所有活动都算；其他人只对自己负责的活动）。
   - `payee`：处理进了自己账户的收款（有 `group` 能力的人对所有收款都算）。
   - `members.read`：只读看成员页和待审核（不含专属链接）。
   - `self`：改自己的收款设置、Telegram。
3. 涉及活动的接口统一先查 `events.manager_id`；涉及付款、收款记录的接口先反查到活动或收款人再判断。**不在处理函数里各自写判断**，避免漏。
4. 加一个测试：遍历所有管理接口，没登记能力的直接测试失败；再对每个 `event`/`payee` 接口用「别人的活动」各打一遍，必须 403。

### 10.2 组织者用的接口和页面
- 复用群主现在的 Google 管理入口 `/admin/google`（接口 `/api/admin/google/*`）：今天这条路径只放行群主的 Google 账号，改成也放行组织者，再由第 10.1 节的权限表决定每个接口能不能用。页面和接口都是同一套，不另写一份，少一半代码，也少一半出错的地方。
- 组织者拿不到群主的管理链接 `/admin/<令牌>`，那条路径只认群主（链接 + 密码）。
- 成员列表、待审核、个人信息接口对组织者只读开放，内容和群主一样，只去掉专属链接；所有改动成员的接口仍只给群主。
- 页面：组织者登录后，顶部多一个「管理」入口，内容是群主管理页的子集：我负责的活动、发起活动、收款（只含自己账户的）、只读的「待审核」和「成员」、我的收款设置、我的 Telegram。没有全局设置、导出这些，成员页上也没有任何操作按钮。
- 群主的活动列表每场显示负责人，可以按负责人筛选。

### 10.3 其他需要跟着改的地方
- 需求文档里「所有人的付款情况只有 Owner 能看到」「Telegram 只发给 Owner」「多出的几分钱归 Owner」「挂在 Owner 名下自动算已付」等规则都要改写成按群主/负责人/收款人的版本。
- `billing.ts` 里「群主自动已付」的逻辑改为收款人。
- `inbound.ts` 的收款人判断和付错人的「待确认」。
- 「可关联账单」列表里「组织者本人的不列」改成「这场收款人本人的不列」，并按身份过滤。
- 健康检查、每周简报按收款人分别统计。
- 导出和 Google 表格多两列：负责人、收款人。
- 「清空所有数据」要把新表一起清掉（`RESET_TABLES`）；`telegram_bindings` 也要清，和现在清 `telegram_chat_id` 一致。
- 迁移回填 `manager_id`/`payee_id` 为群主编号；新建库（还没设置群主）时没有可回填的人也没关系，空值一律当群主（第 5 节）。
- 前端判断「是不是组织者」现在靠 Google 会话接口返回的 `isAdmin`（其实只表示群主），要改成返回 `role`。
- 统计、排行榜不受影响（谁发起的活动都算出勤）。
- 公开页面不显示组织者名字，保持「公开页不出现任何名字」的现有规则；登录成员看到的活动卡片上显示「组织：A」。

## 11. 分步上线

拆成 11 个 PR，顺序和每张卡的内容见 [organizers-tasks.zh.md](organizers-tasks.zh.md)。关键规则：

- **功能开关 `ORGANIZERS`**（`wrangler.jsonc` 里按环境设置）：staging 开、生产关，直到最后一张卡。开关关着时没有人能被任命、组织者进不了管理页，所以中途哪天发布了别的修复，半成品也不会在生产露出来。
- **开关只管入口，不管钱。** 账单显示谁的 Venmo、对账认哪个账户、谁自动算已付，永远按收款人走、不看开关。功能上线后万一要紧急关开关，组织者活动的钱照样能对上。
- **多收款人对账必须和组织者入口一起在生产打开。** 否则组织者活动的 Venmo 付款会因为「收款账号和设置不一致」被丢掉，还会天天给群主报异常。开关在最后一张卡才打开，自然满足这一条。

**回滚风险比以前大。** 有了组织者活动以后，如果回滚到不认识 `payee_id` 的旧版本，旧代码会在组织者活动的账单上显示**群主的** Venmo，成员会把钱付错人。所以打开开关的版本发布之后，除非先恢复数据库备份，不能回滚到更早的版本；发布前要在 staging 上跑通一整场组织者活动（发起 → 报名 → Finalize → Venmo 自动对账 → 收齐）。

每张卡都按现在的流程：写 → 自动审查 → 修 → CI 通过合并到 main（自动部署 staging），生产发布等你说「发布」。
